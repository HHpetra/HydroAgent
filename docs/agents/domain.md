# 领域文档（Domain Docs）

本仓是**单上下文**（根目录只有一份 `GLOSSARY.md`，无 `GLOSSARY-MAP.md`）。以下规则供所有 Agent / skill 在探索代码前遵守。

## 动手前先读

1. 根目录 `GLOSSARY.md` —— 领域语言（服务边界、场景时钟、调洪术语等叫法）。写 issue 标题、测试名、重构提案时用表内词汇，不要漂移到 `_Avoid_` 列出的说法。
2. `docs/adr/` —— 读与你即将改动的区域相关的 ADR。ADR 记的是"为什么这么做"；**不要重新讨论已被 ADR 定下的事**（例如统一用 uv、MCP 服务拆分、场景时钟）。

文件不存在时**静默跳过**：不要提示"缺少 ADR / 术语表"，也不要主动创建。术语或决策真正落定时，由 `domain-modeling` 按需创建。

## 冲突要显式标注

输出与既有 ADR 矛盾时，不许静默覆盖，必须写明：

> 与 ADR-0001（MCP 服务拆分）冲突，但值得重开，因为…

只在摩擦真实存在时才提；不要罗列 ADR 理论上禁止的所有重构。

## 何时新增 ADR

三条**同时**满足才写，缺一条就跳过：

1. **难以回退** —— 以后改主意的代价是实打实的（换包管理器、换传输方式、拆分 / 合并服务都算）
2. **没有上下文会让人困惑** —— 后人看到代码会问"为什么这么做"
3. **真有过取舍** —— 存在被放弃的备选方案，且选它有具体理由
